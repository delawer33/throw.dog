# ADR 0001: Текст передаётся по обычному HTTP, WebSocket — только для файлов

Дата: 2026-08-22. Статус: принято.

## Контекст

Ранняя версия плана выполнения описывала
realtime-сервер как «WebSocket: релей текста + сигналинг WebRTC». Метрика-звезда
продукта — p50 < 10 сек **включая корпоративные сети**, где прокси и файрволы
режут WebSocket заметно чаще, чем обычный HTTPS.

Флоу текста по природе запрос-ответ: отправитель создаёт бросок (POST),
получатель сам инициирует забор, когда набрал URL (GET/POST). Пушить получателю
нечего — он ещё не открыл страницу.

## Решение

- Текстовые броски ходят по чистому HTTP: `POST` на создание, запрос по коду
  на прочтение. Никакого WebSocket в текстовом пути — ни в прототипе, ни в MVP.
- WebSocket появляется только на этапе файлов (этап 2) как сигналинг WebRTC.
- Следствие для ворот этапа 0: замер p50 идёт по тому же HTTP-пути,
  что и боевой текстовый флоу, — результат репрезентативен.

## Альтернативы

- **WebSocket-релей текста** (исходный план): даёт живое «текст получен»
  у отправителя, но добавляет рукопожатие, хуже проходит корпоративные прокси
  и усложняет прототип. Отклонено: пуш-уведомление отправителю добивается
  дешёвым поллингом позже, а надёжность прохода файрволов — часть обещания
  продукта.

## Последствия

- Прототип этапа 0 — два HTTP-эндпоинта + статика, без realtime-слоя.
- «Отправитель видит факт получения» — отложенная фича (поллинг), не блокер.
